План улучшений подпроекта java (бэкенд query-gra)

Сформирован заново по текущему коду, без использования старых «Предложений». Дата: 2026

Цель

Повысить безопасность, надёжность и поддерживаемость JVM-бэкенда (java/: Ktor 3.5.2 + Netty, Kotlin 2.4.10/JVM 25, PostgreSQL + BigQuery, раздаёт фронтенд из classpath).

Краткая оценка текущего состояния

  • 4 файла: Server.kt, Routes.kt, PgSQL.kt, FromJsonString.kt + build.gradle.kts; тестов нет нигде в проекте.
  • Критично: публичный RCE-маршрут, SQL-инъекции, мутации БД без авторизации, гонки на глобальных мутабельных переменных, утечки JDBC-ресурсов, отсутствие пула соединений.
  • Фронтенд использует контракт: POST /jsr223, POST /loadEnv, POST /bd/{name}/passw, GET/POST /bd/{name}/jsonPG..., GET / — менять контракт нельзя без синхронных правок в main/.

P0Безопасность (критично, делать первым)

  1. Удалить RCE-маршрут GET /com/{command} (Routes.kt:36-47): выполняет произвольные OS-команды через Runtime.exec и отдаёт вывод. Удалить совсем; если нужен для отладки — за флагом ENABLE_DEBUG_ROUTES=true + проверка админ-пароля (лучше не оставлять вовсе).
  2. Авторизация мутаций. POST /bd/{name}/jsonPGupd/{pg_view}/{where?} (Routes.kt:64-73) сейчас без проверки — любой может UPDATE/DELETE/INSERT. Ввести обязательный заголовок X-Admin-Token (значение = ADMIN_PASSW env или подписанный токен), проверку вынести в общий хелпер. Синхронно поправить main/src/jsMain/kotlin/ApiQuerys.kt (передавать токен из adminState при сохранении).
  3. SQL-инъекции. Заменить построение SQL конкатенацией на PreparedStatement во всех путях:
    • jsonPGview (PgSQL.kt:101-137): where и pg_view подставляются в текст запроса; name интерполируется в where name = '$name'.
    • checkInjection (PgSQL.kt:161-164) — чёрный список (OR, ;, SELECT…) легко обходится (union select, комментарии, \n, обфускация регистра). Заменить политикой: allowlist имён представлений + строгая валидация where-выражения (разрешённые токены/операторы), параметры — через PreparedStatement.
    • insertParameterValue (shared/CommonVars.kt:76-87) — замена {key} сырыми значениями без экранирования. Заменить на подстановку параметров (?), значения передавать отдельно.
    • formSQLQuery (PgSQL.kt:183-226): экранирование '' в E'...' не покрывает backslash-инъекции (для E-строк \ — escape-символ). После перехода на параметризованные запросы экранирование не нужно вовсе.
  4. CORS: anyHost() (Server.kt:36) заменить на allowlist из env (CORS_ORIGINS).
  5. Ограничения входа: лимит размера тела (call.receive), максимальная длина where/pg_view, базовый rate-limiting на мутационные маршруты.
  6. JSR223 (Routes.kt:18-25, runScript 109-118): серверная реализация полностью закомментирована (функция фактически мертва, фронтенд F9 шлёт src). Решить: либо удалить маршрут, либо реализовать на kotlin-scripting-jsr223 с песочницей (запрет Runtime, лимит времени/памяти). Рекомендация — реализовать минимально с жёсткими ограничениями, т.к. функция заявлена в help.html.

P1Корректность и надёжность

  1. Гонки на глобальном состоянии:
    • FromJsonString.kt:10-16: QUOTE_TYPE и mappingFun — глобалы, выставляемые перед декодированием; два параллельных jsonPGupd с разными кавычками перепутают экранирование → порча данных. Убрать глобалы, передавать quoteType/функцию параметром.
    • Routes.kt:19: rowFieldsValueMap = call.receive() — замена общего глобала из shared из тела запроса. Убрать мутацию, держать локально.
    • connectionError, message, loadTestingKeys, queryBdName, connectionsMap, startEnv — глобалы без синхронизации. После рефакторинга (P2) состояние живёт в сервисных классах; startEnv — неизменяемый конфиг, читаемый только при старте.
  2. Пул соединений и ресурсы: заменить ручной кэш DriverManager-соединений (PgSQL.kt:35-72) на HikariCP (per-база пул, maximumPoolSize из env). Все Statement/ResultSet закрывать через use { } (сейчас утечки в rezSQL 139-159, pgsqlJson 239-256, jsonPGupd 166-181). При retry-ошибке (SQL_STATE_RETRY) закрывать старый коннект перед заменой.
  3. Баг rezSQL: onFailure { (it as PSQLException) } (PgSQL.kt:156) — не-PSQLException (таймаут, сетевая ошибка) роняет запрос ClassCastException'ом. Проверять is PSQLException.
  4. splitURL (PgSQL.kt:23-33): хрупкий парсинг по индексам (ломается на IPv6, @/: в пароле). Заменить на разбор через java.net.URI (или передавать готовый JDBC URL).
  5. SSL root cert (PgSQL.kt:93-98): писать в ./$baseName.crt — относительный путь и имя из имени базы (коллизии, read-only ФС контейнера). Писать в java.io.tmpdir с именем по хэшу строки.
  6. Транзакции для jsonPGupd: сейчас N строк склеены в один много-операторный запрос; при частичной ошибке данные остаются полу-изменёнными. Обернуть в BEGIN/COMMIT/ROLLBACK (или батчи + savepoints). Определение первичных ключей — через JDBC getPrimaryKeys вместо эвристики idFieds (PgSQL.kt:228-231).
  7. Двойное выполнение при retry: getView (Routes.kt:80-86) вызывает getView(it) дважды при retry-ошибке — выполнить один раз, повторно лишь при реальном восстановлении соединения.
  8. BigQuery: задать явный таймаут запроса (QueryJobConfiguration.setJobTimeoutMs), закрывать/освобождать job.

P2Архитектура и качество кода

  1. Разбить top-level-функции/глобалы на классы: AppConfig (env-конфиг, валидация при старте), DatabaseManager (пулы, соединения, sslrootcert), SqlBuilder (генерация SQL, allowlist), JsonMapper (чистый fromJsonString без глобалов).
  2. Установить StatusPages (единый JSON-формат ошибок вместо сырых 500) и CallLogging (лог с X-Request-ID, без SQL-значений в логах — сейчас println выводит запросы с данными, потенциально PII).
  3. Удалить мёртвый код: runScript (всё закомментировано), nodeVer() (build.gradle.kts:137-138, не используется), myProp()-запись в src (см. P3), блок distributions c from("$projectDir/libs") (build.gradle.kts:98-109 — папки java/libs не существует), зависимость ktor-websockets (не используется), неиспользуемые константы/импорты.
  4. errorJson (PgSQL.kt:275-276) строит JSON строкой с replace("\"","") — риск битого JSON; собрать через kotlinx.serialization JsonObject.
  5. Добавить GET /healthz → 200 {"status":"ok"} (+ проверка пулов) для startup/liveness-проб Cloud Run.

P3Сборка (Gradle)

  1. myProp() (build.gradle.kts:139-160): пишет config.properties в java/src/jvmMain/resources на каждую конфигурацию сборки — грязнит git, нерепроизводимо (timestamp), требует git/node на машине сборки, тормозит любую команду (gradle help тоже). Перенести генерацию в build/generated/… (или в ресурсы из build-каталога), файл в src из VCS убрать; версию собирать из version + gitCommitHash() (с fallback, если git недоступен).
  2. isDevelopmentRun (build.gradle.kts:77) — хрупкая проверка имени таски; заменить на проект-свойство -Pdev (конфигурация-кэш-дружелюбно).
  3. Версии — в version catalog (gradle/libs.versions.toml); включить dependency locking для воспроизводимых сборок; group/version в одном месте.
  4. Добавить ktlint/detekt и GitHub Actions CI (:java:build :java:test).
  5. Упростить связку processResources ↔ :main:build (сохранить логику prod/dev, но без жёсткой привязки к имени таски).

P4Тесты (в модуле java нет ни одного)

  1. Юнит-тесты чистых функций после рефакторинга: парсинг URL, formSQLQuery (без экранирования-глобалов), allowlist-валидатор where, fromJsonString, сборка errorJson, генерация конфига.
  2. ktor-server-test-host (testApplication): маршруты — 401 на мутации без токена, отсутствие/закрытость /com/, валидность JSON-ответов.
  3. (Опционально) Testcontainers PostgreSQL для интеграционных проверок jsonPGview/jsonPGupd (transaction + параметризация).

Краевые случаи и риски:
  • Контракт API: правки P0/P1 не меняют имена/формат маршрутов (кроме удаления /com/ и, возможно, jsr223). Изменение ответа passw-маршрута не требуется.
  • JSR223: фронтенд вызывает его (F9) — при удалении маршрута обновить main/ (убрать вызов) и help.html; при реализации — строгая песочница.
  • config.properties: после переноса генерации в build/ убедиться, что Dockerfile/Procfile не ждут файл в src; Docker-сборки пересобрать (:java:installDist).
  • Cloud Run: containerConcurrency: 80 — до фикса глобалов параллельные запросы могут искажать данные; выкатывать Фазу 2 сразу после Фазы 1.
  • Регресс фронтенда: проверять после Фазы 1 на live-окружении (edit/delete в таблице с админ-паролем).

Критерии приёмки

  1. Маршрут /com/ отсутствует (или недоступен без флага+токена) — тест в testApplication.
  2. POST jsonPGupd без валидного токена → 401; с токеном → работает (тест).
  3. В коде нет конкатенации пользовательских значений в SQL — только PreparedStatement (проверка grep по $where/$name/$bdName в строках запросов).
  4. Параллельный прогон двух jsonPGupd с разными кавычками не искажает данные (ручная проверка + тест).
  5. ./gradlew :java:test зелёный; ./gradlew :java:build не изменяет файлы в src (git status чист после сборки).
  6. /healthz отвечает 200 на Cloud Run.
